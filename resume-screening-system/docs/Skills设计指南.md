# Skills 设计指南

> **核心观点**：每个企业都应该根据自身的公司特点、行业属性和岗位需求，设计专属的 Skills。直接套用通用模板会导致筛选效果大打折扣。

## 为什么不能直接用通用模板

### 问题一：同一岗位，不同公司需求完全不同

以"Java 工程师"为例：

| 公司类型 | 核心需求 | 评分重点 |
|---------|---------|---------|
| **互联网大厂** | 高并发、分布式系统、海量数据处理 | 系统设计能力、技术深度 |
| **金融科技** | 安全合规、事务一致性、稳定可靠 | 金融业务理解、风控意识 |
| **传统企业 IT** | 业务系统维护、快速响应需求 | 沟通能力、业务理解力 |
| **AI 创业公司** | AI 集成、Prompt Engineering、Agent 开发 | AI 工具使用、学习速度 |
| **外包公司** | 快速上手、多项目切换 | 学习能力、适应性 |

**直接用"通用 Java 工程师"模板的后果：**
- 互联网公司可能错过系统设计高手
- 金融公司可能招到不懂合规的技术宅
- AI 公司可能招到不会用 AI 工具的传统开发

### 问题二：公司文化决定了"什么样的人能留下来"

技术能力只是一部分，公司文化匹配度同样重要：

| 公司文化 | 应该在 Skills 中体现 |
|---------|-------------------|
| 狼性文化 | 抗压能力、自驱力、目标导向 |
| 工程师文化 | 代码洁癖、技术追求、开源贡献 |
| 扁平化 | 主动性、跨团队协作、独立决策 |
| 流程导向 | 文档能力、规范意识、细节把控 |
| 创新驱动 | 创造力、试错精神、新技术敏感度 |

### 问题三：团队现状决定了"需要互补什么"

同样的岗位，团队不同阶段需求不同：

- **团队初创期**：需要多面手，一个人顶多人用
- **团队扩张期**：需要专才，在某个方向深耕
- **团队成熟期**：需要传帮带的人，有培养新人能力
- **团队转型期**：需要带来新思路、新技术的人

### 第二步：定义岗位核心价值

问自己：**这个岗位存在的根本价值是什么？**

```
岗位价值公式：
岗位核心价值 = 解决什么问题 + 创造什么价值 + 需要什么核心能力
```

**示例：**

| 岗位 | 解决什么问题 | 创造什么价值 | 核心能力 |
|------|------------|------------|---------|
| Java 工程师（电商） | 系统稳定性、高并发处理 | 用户体验、交易成功率 | 高并发设计、问题排查 |
| HR 专员（招聘） | 快速找到合适的人 | 降低招聘成本、提升招聘质量 | 人才识别、沟通协调 |
| 产品经理 | 用户需求与技术实现的桥梁 | 产品价值、用户增长 | 需求分析、优先级判断 |

### 第三步：设计评估维度和权重

基于岗位核心价值，设计 4-6 个评估维度，并分配权重。

**权重分配原则：**
- 核心价值相关的维度，权重应该最高（25-35%）
- 辅助能力的维度，权重适中（15-25%）
- 加分项类的维度，权重较低（10-15%）
- 所有权重加起来必须等于 100%

**示例：互联网大厂 Java 工程师**
```
┌──────────────────────────────────────┐
│ 维度                      │ 权重    │
├──────────────────────────────────────┤
│ 系统设计能力               │ 30%    │ ← 核心（高并发场景决定成败）
│ 技术深度                   │ 25%    │ ← 核心（技术底子决定上限）
│ 项目经验                   │ 20%    │ ← 重要（验证实战能力）
│ 工程素养                   │ 15%    │ ← 辅助（代码质量、协作效率）
│ 学习与AI能力               │ 10%    │ ← 加分（持续成长潜力）
├──────────────────────────────────────┤
│ 合计                       │ 100%   │
└──────────────────────────────────────┘
```

**示例：传统企业 Java 工程师**
```
┌──────────────────────────────────────┐
│ 维度                      │ 权重    │
├──────────────────────────────────────┤
│ 业务理解能力               │ 30%    │ ← 核心（能理解业务才能做对）
│ 沟通协作能力               │ 25%    │ ← 核心（跨部门协作频繁）
│ 技术实现能力               │ 20%    │ ← 重要（能做出来是底线）
│ 问题解决能力               │ 15%    │ ← 辅助（线上问题要能扛）
│ 文档与规范                 │ 10%    │ ← 加分（交接、维护方便）
├──────────────────────────────────────┤
│ 合计                       │ 100%   │
└──────────────────────────────────────┘
```

**注意**：同样是"Java 工程师"，不同类型公司的权重分配完全不同！

### 第四步：细化评分标准

每个维度的 1-5 分，必须有明确的定义，让 AI 有据可依。

**好的评分标准示例：**
```
【系统设计能力】权重 30%

5分 = 优秀：
- 主导过千万级 DAU 系统设计
- 有完整的高可用方案经验（多机房、容灾）
- 简历中有明确的性能优化量化成果

4分 = 良好：
- 参与过百万级系统设计
- 熟悉常见高可用方案
- 有一定的性能优化经验

3分 = 合格：
- 了解分布式系统基本概念
- 做过一些性能优化尝试
- 系统规模较小但有完整经验

2分 = 较弱：
- 只做过单体应用
- 缺乏系统设计经验
- 没有性能优化相关经历

1分 = 不合格：
- 完全没有系统设计概念
- 只写过 CRUD 代码
```

**差的评分标准示例（不要这样做）：**
```
5分 = 很好
4分 = 好
3分 = 一般
2分 = 差
1分 = 很差
```
这样的标准太模糊，AI 无从判断，结果随机性大。

### 第五步：设计硬性门槛

硬性门槛是"一票否决"项，不符合直接淘汰，不进入评分环节。

**门槛设计原则：**
- 只设置真正必须的条件
- 能后期培养的不设为门槛
- 可替代的条件慎设门槛

**示例：**
```
【硬性门槛】不符合任意一项直接淘汰

必选门槛（不可替代）：
- 本科及以上学历
- 3年以上 Java 开发经验
- 熟悉 Spring 框架

可选门槛（根据实际情况）：
- 计算机相关专业（非必须，如有丰富项目经验可放宽）
- 特定行业经验（如金融行业必须有金融背景）
```

## 不同公司类型的 Skills 差异

### 互联网大厂

**特点**：高并发、分布式、海量数据、快速迭代

**Skills 重点**：
- 系统设计能力（权重高）
- 技术深度（JVM、多线程、中间件）
- 大规模系统经验
- 数据驱动思维

**示例评分维度**：
```
1. 系统设计能力 - 30%
2. 技术深度 - 25%
3. 项目规模与质量 - 20%
4. 工程素养 - 15%
5. AI与学习能力 - 10%
```

### 金融科技

**特点**：安全合规、稳定可靠、事务一致性

**Skills 重点**：
- 金融业务理解
- 安全与合规意识
- 稳定性保障经验
- 细节把控能力

**示例评分维度**：
```
1. 金融业务理解 - 25%
2. 安全与合规 - 25%
3. 技术实现能力 - 20%
4. 稳定性保障 - 20%
5. 沟通与文档 - 10%
```

### 传统企业 IT

**特点**：业务驱动、稳定优先、跨部门协作多

**Skills 重点**：
- 业务理解能力
- 沟通协作能力
- 问题解决能力
- 文档与规范

**示例评分维度**：
```
1. 业务理解能力 - 30%
2. 沟通协作能力 - 25%
3. 技术实现能力 - 20%
4. 问题解决能力 - 15%
5. 文档与规范 - 10%
```

### AI 创业公司

**特点**：快速变化、AI 驱动、创新导向

**Skills 重点**：
- AI 工具使用能力
- 学习速度与适应性
- 创新与试错精神
- 全栈/多面手能力

**示例评分维度**：
```
1. AI工具与开发能力 - 30%
2. 学习速度与适应性 - 25%
3. 技术广度（全栈） - 20%
4. 创新与试错 - 15%
5. 项目经验 - 10%
```

## Skills 设计常见误区

### 误区一：照搬行业模板

**错误**："别人公司用这个模板，我们也用"

**问题**：每个公司的文化、业务、团队都不同，照搬无法匹配实际需求

**正确做法**：基于模板，根据公司特点定制调整

### 误区二：维度太多太细

**错误**：设置 10+ 个评分维度

**问题**：维度过多导致权重分散，重点不突出，评估耗时长

**正确做法**：4-6 个维度足够，突出核心能力

### 误区三：评分标准模糊

**错误**：5分=很好，4分=好，3分=一般...

**问题**：AI 无从判断，结果随机性大

**正确做法**：每个分数都有具体、可衡量的定义

### 误区四：门槛设置过严

**错误**：硬性要求"985本科 + 5年经验 + 大厂背景"

**问题**：过滤掉大量潜力候选人，招聘难度增大

**正确做法**：只设置真正必要的门槛，其他作为加分项

### 误区五：忽视 AI 时代能力

**错误**：Skills 中完全不考虑 AI 工具使用能力

**问题**：AI 已成为生产力工具，不会用 AI 的候选人竞争力下降

**正确做法**：适当加入 AI 工具使用能力的评估

### 误区六：一成不变

**错误**：设计好的 Skills 几年不更新

**问题**：技术栈变化、业务方向调整、团队需求变化

**正确做法**：定期（至少每年）review 和更新 Skills

## 案例分析

### 案例：某 AI 创业公司招聘全栈工程师

**公司背景**：
- 20人 AI 初创公司
- 做 AI Agent 产品
- 快速迭代、创新驱动

**传统 Skills（不适合）**：
```
维度：技术深度 30%、工作经验 25%、学历背景 20%...
```
问题：过于关注传统指标，忽视了 AI 公司的特殊需求

**定制 Skills（适合）**：
```
维度1：AI工具使用能力 - 30%
  5分 = 熟练使用 Claude/GPT 进行开发，有 Agent 开发经验
  4分 = 日常使用 AI 辅助编码，了解 Prompt Engineering
  3分 = 偶尔使用 AI 工具
  2分 = 听说过但很少用
  1分 = 从未使用

维度2：全栈开发能力 - 25%
  5分 = 前后端 + 部署 + 数据库全栈独立交付
  4分 = 前后端熟练，部署有经验
  3分 = 专精一端，另一端能看懂
  ...

维度3：学习与适应速度 - 20%
  5分 = 有快速学习新技术的量化案例（如2周上手新框架）
  4分 = 技术栈丰富，切换顺畅
  ...

维度4：项目交付能力 - 15%
  ...

维度5：创新与试错精神 - 10%
  ...
```

**效果**：筛选出的候选人真正适合 AI 创业公司的需求。

## 总结

1. **Skills 设计是战略决策**：决定了你能招到什么样的人
2. **必须根据公司特点定制**：照搬模板会事倍功半
3. **定期更新 Skills**：业务变化、技术演进都需要调整
4. **权重分配体现价值观**：什么维度权重高，说明公司看重什么
5. **评分标准要具体可衡量**：模糊的标准 = 随机的结果

---

*Skills 设计好了，才是 AI 招聘成功的开始。*
